## 2025-02-23 - Global Variable Initialization Race Condition
**Vulnerability:** Critical secrets (JWT_SECRET) were initialized in global variables using `os.Getenv` at package load time.
**Learning:** In Go, package `init` and global variable initialization happen *before* `main()` runs. Since `godotenv.Load()` was called in `main()`, the global variables captured the empty environment (or system env) *before* the `.env` file was loaded. This resulted in the application running with empty secrets (e.g., empty JWT key) when relying on `.env`, allowing authentication bypass.
**Prevention:** Avoid initializing secrets in global variables at the top level if they depend on runtime configuration loading (like `.env`). Use lazy-loading functions (getter pattern) or initialize globals explicitly after configuration loading is complete.
## 2025-02-23 - Unhandled NULL from SQL Aggregations
**Vulnerability:** SQL aggregation functions like `SUM()` can return `NULL` when there are no matching rows (e.g., when filtering by a date range where the user has no transactions). Because the application was directly scanning these into float64 variables, it caused unhandled runtime panic/errors ("converting NULL to float64 is unsupported").
**Learning:** This crashes the endpoint and returns raw generic "Database error" to the client, leading to a poor UX and potentially a Denial of Service if the endpoint is critical, while also logging internal scan errors.
**Prevention:** Always wrap SQL aggregation functions (like `SUM()`, `MIN()`, `MAX()`, `AVG()`) with `COALESCE(..., 0)` when the result might be scanned into a primitive non-nullable Go type (like `float64`), or explicitly use `sql.NullFloat64` in Go.
