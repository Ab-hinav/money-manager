## 2025-02-23 - Global Variable Initialization Race Condition
**Vulnerability:** Critical secrets (JWT_SECRET) were initialized in global variables using `os.Getenv` at package load time.
**Learning:** In Go, package `init` and global variable initialization happen *before* `main()` runs. Since `godotenv.Load()` was called in `main()`, the global variables captured the empty environment (or system env) *before* the `.env` file was loaded. This resulted in the application running with empty secrets (e.g., empty JWT key) when relying on `.env`, allowing authentication bypass.
**Prevention:** Avoid initializing secrets in global variables at the top level if they depend on runtime configuration loading (like `.env`). Use lazy-loading functions (getter pattern) or initialize globals explicitly after configuration loading is complete.
## 2024-05-24 - JWT Algorithm Confusion Vulnerability in AuthMiddleware
**Vulnerability:** The `jwt.ParseWithClaims` function in `backend/internal/api/middleware.go` did not verify the signing method (`token.Method`) before returning the secret key. This allowed potential JWT algorithm confusion attacks where an attacker could change the algorithm to "none" or use a public key as an HMAC secret.
**Learning:** The `golang-jwt` library requires explicit validation of the signing method within the `Keyfunc` to ensure the token was signed with the expected algorithm (e.g., HMAC). Omitting this check creates a severe security risk.
**Prevention:** Always assert the type of `token.Method` (e.g., `if _, ok := token.Method.(*jwt.SigningMethodHMAC); !ok`) inside the `Keyfunc` callback of `ParseWithClaims` and return an error (like `jwt.ErrSignatureInvalid`) if it doesn't match the expected algorithm.
