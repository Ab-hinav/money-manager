To define the requirements for a comprehensive financial management application that provides users and organizations with a clear view of their expenses, savings, and overall financial health. This document will serve as the primary source of truth for development, a reference point for tracking tasks, and a learning aid for the creator.

2. Goals and Objectives

The primary goal of the Money Manager app is to empower users and organizations to achieve better financial control and awareness.
Financial Clarity: Provide a clear, real-time visualization of all financial activities (income, expenses, savings).
Effective Tracking: Allow for easy and accurate logging and categorization of expenses and income.
Progress Reference: Create a single reference point for the entire project lifecycle, including tasks completed and future plans, ensuring all stakeholders (including LLMs like Gemini and Stich) are "on the same page."
Learning & Hands-On Experience: Serve as a project to help the creator learn and gain hands-on experience with the chosen technology stack.
3. Target Audience
Individual Users: People seeking to track personal spending, set budgets, and manage savings goals.
Organizations (Small to Medium): Entities needing a simple, clear tool to monitor organizational expenses, manage department budgets, and track overall cash flow.

Here are the detailed goals and expectations for Phase 1: Core App development, focused on establishing the Minimum Viable Product (MVP) and the foundational technology stack.Phase 1: Goals and Expectations

The primary expectation for Phase 1 is the delivery of a fully functional, end-to-end core financial tracking application that is stable and ready for internal testing.

1. Core Feature Implementation (Functional Goals)
User Authentication & Authorization:
Goal: Implement a secure registration, login, and session management system.
Expectation: Users must be able to securely create an account and log in. All core feature access must be behind this authentication layer.
Transaction Logging (Expense & Income):
Goal: Enable users to quickly and accurately log both income and expenses.
Expectation: The application must support manual entry of: Amount, Date, Description, Category (must be customizable), and an associated Account. Recurring transactions must also be supported.
Account Management:
Goal: Allow users to manage their different money sources.
Expectation: Users must be able to create, name, and set an initial balance for multiple accounts (e.g., Bank, Credit Card, Cash). Transaction logging must correctly update the corresponding account balance.
Dashboard & Reporting (Basic):
Goal: Provide an immediate, clear overview of the user's financial status.
Expectation: A basic dashboard view must be operational, displaying:
Total Net Worth/Current Balance across all accounts.
Simple charts showing total income vs. total expenses for the current month.
A breakdown of expenses by category for the current month.
2. Technical Foundations (Non-Functional Goals)
Technology Stack Setup:
Goal: Establish a stable and scalable initial architecture based on the defined stack.
Expectation: The live environment must have:
Frontend: Next.js application hosted on AWS.
Backend: GoLang API services running as containers.
Database: Postgres instance provisioned and running, successfully handling transaction integrity and data persistence.
Infrastructure (MVP Baseline):
Goal: Deploy a lean, secure, and cost-effective infrastructure on AWS.
Expectation: A minimal Kubernetes cluster (K8s) must be set up to host only the necessary backend services. The chosen DB Deployment strategy (either EC2-hosted Postgres or a managed service) must be finalized and implemented.
Project Learnings:
Goal: Successfully complete the end-to-end deployment to gain hands-on experience.
Expectation: The creator must document lessons learned during the setup of the Next.js/GoLang interaction, database schema design, and AWS/Kubernetes deployment process. This documentation will be a continuous, internal resource.



PRD Addendum: Phase 1 Technical Architecture
Date: 18-Jan-26
Status: Approved
Context: MVP / Phase 1 Implementation
1. Architecture Overview
For Phase 1, we are adopting a 3-Tier Managed Architecture leveraging the AWS Free Tier. This balances the goal of "Learning Kubernetes" with the need for a stable, production-grade database.
Pattern: Hybrid Cloud/Cluster (Managed Database + Self-Managed Kubernetes).
Infrastructure Provider: AWS (Free Tier eligible).
2. Technology Stack Decisions
Component
Selected Technology
Specification/Configuration
Frontend
Next.js
App Router architecture. Initially deployed via Vercel or containerized in K8s (TBD based on CI/CD preference).
Backend
Go (Golang)
Monolithic architecture (initially). Uses net/http or Chi router. Packaged as a Docker container.
Database
AWS RDS
PostgreSQL engine. Managed service to ensure data persistence, automated backups, and high availability.
Orchestration
K3s
Lightweight Kubernetes distribution running on a single EC2 node. Replaces heavy EKS for cost efficiency.

3. Infrastructure Specifications (AWS)
A. Database Layer (The "State")
Service: Amazon RDS (Relational Database Service).
Instance Type: db.t3.micro (Free Tier eligible).
Storage: 20 GB General Purpose SSD (gp2).
Access: Private restriction. Only accessible via the Application Security Group.
B. Compute Layer (The "Cluster")
Service: Amazon EC2.
Instance Type: t3.medium (Preferred for K8s stability) or t3.micro (Minimum viable).
OS: Ubuntu 22.04 LTS.
Role: Single-Node K3s Cluster (Acts as both Control Plane and Worker Node).
C. Networking & Security
Security Group (money-app-sg):
Inbound: Allow HTTP/HTTPS (Web), SSH (Admin only), K8s API (Admin only).
Internal: RDS allows traffic only from money-app-sg (Self-referencing rule).
4. Decision Rationale (Why this architecture?)
Stability vs. Learning: By moving the database out of Kubernetes and into RDS, we eliminate the risk of data loss due to pod crashes or misconfigured Persistent Volumes. We still get full Kubernetes learning value by hosting the API and Frontend in the cluster.
Cost Optimization: The stack maximizes the AWS Free Tier (t3.micro instances) while using K3s to avoid the high control-plane costs of AWS EKS.
Simplicity: Starting with a backend monolith avoids the complexities of distributed tracing and service mesh networking in Phase 1.

1. Overview
While Phase 1 focused on infrastructure and data entry, Phase 2 shifted focus to data utility and active management. The application now allows users to not just log transactions, but to set targets (Goals), define limits (Budgets), and edit historical data.

2. Functional Features Delivered

Feature Area
Description
Implementation Details

Composite Dashboard
A unified "Financial Pulse" view that aggregates 5 distinct data sources into a single screen.
Backend: Implemented individual API endpoints for specific dashboard metrics (Income, Expense, Savings, etc.) allowing modular data fetching.
Frontend: Modular UI cards for Income/Expense, Net Worth, and Top Spends.

Unified Goal & Budget Engine
A system to track both "Savings Targets" (Accumulators) and "Expense Limits" (Thresholds) using a shared architecture.
Logic: Implemented a 'type' flag ('SAVING' vs 'BUDGET').
Behavior: 'SAVING' calculates lifetime contributions. 'BUDGET' calculates current-month spending against a limit.

Transaction Linkage
The ability to attribute specific transactions to broader financial goals.
UX: Added "Goal/Budget" dropdown in the Add Transaction form.
DB: Transactions now carry a Foreign Key linking them to parent goals.

Full CRUD Operations
Maturity of the transaction handling system.
Users can now Edit existing transactions (fixing amounts/categories) and Delete erroneous entries, with automatic re-calculation of account balances.

Financial Segmentation
Distinct handling for non-standard transaction types.
Loans: Tracking of EMI payments.
Investments: Tracking of capital contributions separate from standard "Expenses."


3. Technical Architecture Updates (Phase 2)

A. Database Schema Evolution
The centralized 'transactions' table was enhanced, and a new 'goals' entity was introduced.
-- New Table: 'goals'
   Fields: id, user_id, name, target_amount, current_amount, type (Enum: SAVING, BUDGET), color, icon.
-- Modified Table: 'transactions'
   Update: Added 'goal_id' (FK) to allow Many-to-One relationship with Goals.
   Constraint: ON DELETE SET NULL (Preserves transaction history even if a goal is deleted).

B. API Strategy:

-- Endpoint: GET /api/dashboard/total-balance
-- Endpoint: GET /api/dashboard/total-income
-- Endpoint: GET /api/dashboard/total-expenses
-- Endpoint: GET /api/dashboard/total-savings
-- Endpoint: GET /api/dashboard/total-loans
-- Endpoint: GET /api/dashboard/total-investment
-- Payload: Individual endpoints return specific JSON objects for Balance, Income, Expenses, Savings, Loans, and Investments.

C. Backend Logic (Go)
-- ACID Compliance: Implemented database transactions to ensure that when a Transaction is added/edited, the 'current_amount' in the linked Goal/Budget is updated atomically.
-- Budget Logic: Added specific date-range filtering to ensure "Expense Budgets" only sum up transactions from the current month (resetting logic).
